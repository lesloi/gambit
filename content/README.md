# Content

What the app ships besides its code. Everything here is generated by a script and committed, so a
clone, a build and a release never reach a third party: only a regeneration downloads something.

## Puzzle subset

`puzzles.jsonl.gz` holds 12,000 puzzles from the public [Lichess puzzle
database](https://database.lichess.org/#puzzles), released under CC0. One JSON object per line, in
the shape the app reads:

```json
{
  "id": "005gP",
  "fen": "8/8/3p4/2kP2P1/1p6/2pK4/P7/8 b - - 0 42",
  "solution": ["c5d5", "g5g6"],
  "rating": 1723,
  "themes": ["enPassant", "pawnEndgame"]
}
```

- `fen` is the position **where the user plays**: the opponent's first move of the Lichess line is
  already applied.
- `solution` is the rest of the line in UCI, starting with the user's move; the sides alternate.
- `themes` are the motifs only. Tags that describe the export (`short`, `crushing`, `middlegame`,
  `master`…) are left out: a motif is what the puzzle teaches once it is solved.

The app fetches this archive from its own origin and decompresses it in the browser, so nothing
leaves the origin and the content stays out of the JS bundle.

`manifest.json` records where the file came from and what it holds: the export's Last-Modified
date, the SHA-256 of the CSV that was read, the filters, the counts per motif and per rating band,
and the SHA-256 of both the archive and the JSONL. The export is a single rolling file, so there is
no dated archive: the checksum is what identifies the snapshot.

### Regenerating it

The rules live in the header of [`scripts/build-puzzles.ts`](../scripts/build-puzzles.ts). From a
checkout, with [zstd](https://facebook.github.io/zstd/) installed:

```sh
curl -sSLO https://database.lichess.org/lichess_db_puzzle.csv.zst
curl -sSI https://database.lichess.org/lichess_db_puzzle.csv.zst | grep -i last-modified
zstd -d lichess_db_puzzle.csv.zst
sha256sum lichess_db_puzzle.csv    # the csvSha256 of the current manifest
pnpm content:puzzles -- lichess_db_puzzle.csv --last-modified "2026-10-02T08:51:45Z"
```

The run takes about half a minute, reads the export twice and prints what it rejected. Two runs from
the same export produce the same bytes, including the gzip header: the output only changes when the
export, the filters or the rules change.

Then check that the app still builds and commit `content/` with the script change, so the two never
drift apart:

```sh
pnpm test && pnpm build
git add content scripts
```

The puzzles are attributed to Lichess in [CREDITS.md](../CREDITS.md).

## Endgame positions

`endgames.json` holds the curated endgames: the position, the side the user plays (the side to
move in the FEN), the expected result (`win` or `draw`) and a one-line goal. The app plays the
other side with Stockfish and checks the conversion locally: mate, insufficient material,
stalemate, the fifty-move rule or a threefold repetition. A `win` card is solved only by mate;
a `draw` card by any drawn end. The set is small on purpose: each position is checked by hand,
and more arrive with the endgame content issue.

The engine that serves them is the `lite single-threaded` build of Stockfish.js, kept unmodified
in [`public/stockfish`](../public/stockfish) and attributed in [CREDITS.md](../CREDITS.md).

## Opening lines

`openings.json` holds the curated repertoire: one entry per line, with a stable id, a name, the
colour the user plays (`color`) and the moves in UCI from the initial position. The app answers
for the other side; a line may stop on either side's move, and it is a card: an attempt is scored
as a whole, not move by move.

```json
{
  "id": "london-vs-d5",
  "name": "London contre ...d5",
  "color": "white",
  "moves": ["d2d4", "d7d5", "c1f4", "g8f6", "e2e3"]
}
```

The moves are book moves written by hand, checked for legality, not engine-verified: an engine
would say what is best, not what the repertoire plays. The set covers the London and Queen's
Gambit with White and the French and Slav with Black; it follows standard theory, not a single
published source. A move outside the line stops the attempt and names the expected one; the
alternatives are strict on purpose. Sibling lines deliberately share their first moves, so
revising one repeats a prefix of another: that redundancy is the training, not a defect.

The parser is strict about the colour: a line must contain at least one move for the user, and
every move must be legal from the initial position.
